# Coronial Recommendation Coding Guide — v2.3

**Status:** Working version, post v2.2 pilot. v2.3 is a **three-sub-rule revision** of v2.2 that finishes off the disagreement classes that the v2.2 pilot surfaced. v2.2 succeeded on its targeted axis (mechanism α 0.541 → 0.870) and confirmed the v2.1 addressee/scope drops as sample-drift (addressee α 0.773 → 0.846), but exposed three new patterns:

| Axis | v2.2 clean α | What v2.3 changes |
|---|---:|---|
| theme | 0.815 ✅ | unchanged |
| mechanism | 0.870 ✅ | one sub-rule (Q3 endpoint test for FUND) |
| addressee | 0.846 ✅ | unchanged |
| specificity | 0.775 ⚠️ | three small clarifications |
| **scope** | **-0.162** ❌ | **major re-framing as intervention-type, not addressee-scope** |

The scope α went negative because two genuinely-independent coders applied two coherent but different readings of the v2.2 codebook: one read "names a single hospital → SCOPE-IND" literally, the other read "creates an ongoing policy → SCOPE-SYS regardless of addressee". Both readings were defensible from the v2.2 text. The fix is structural: re-frame scope so it carries a single conceptual job (what kind of change), letting the addressee axis carry the "who" job alone.

**Unit of analysis** and **coding decision** unchanged from v2.2.

## Axis 2 — Mechanism (decision tree, v2.3)

*Unchanged categories.* Six mutually-exclusive: LEG, INFRA, FUND, INV, PROC, OTHER.

### Decision tree (Q1..Q6, v2.3 — one Q3 wording change)

1. **Q1 — Does the recommendation require amending a statute, regulation, or statutory code of practice?** → **MECH-LEG**.
2. **Q2 — Does the recommendation require installing, replacing, or supplying physical equipment or infrastructure?** → **MECH-INFRA**.
3. **Q3 — Is the recommendation's operational endpoint allocating money, FTE, or positions?** → **MECH-FUND**.
 - *(v2.3 change from v2.2: was "Is the recommendation purely about allocating money, FTE, or positions, with no other operational action?".)* The "purely" qualifier failed when funding bundled with a wrapping "consider" or "review" verb. The endpoint test is the parallel of v2.1's INV ↔ PROC fix that worked.
4. **Q4 — Is the recommendation an external audit, inquiry, or review **as an endpoint** (the deliverable is the review report itself, not a downstream change)?** → **MECH-INV**.
5. **Q5 — Does the recommendation specify a policy, protocol, guideline, SOP, escalation pathway, staff training programme, non-statutory industry standard, curriculum, or other procedural change?** → **MECH-PROC**.
6. **Q6 — None of the above.** → **MECH-OTHER**.

### The Q3 endpoint test (FUND ↔ PROC) — new in v2.3

**Ask the operational-endpoint question for funding/staffing recommendations exactly as you do for INV ↔ PROC.** When the recommendation reaches the FUND tree (Q3 fires), check: is allocating money, FTE, or positions what the recommendation is *satisfied by*? If yes → **MECH-FUND**. If the allocation is one component of a broader procedural change (training programme, policy implementation, service redesign), the broader change is the endpoint → **MECH-PROC**.

**Worked examples:**

| Text | Endpoint | Code |
|---|---|---|
| "Royal Darwin Hospital should give consideration to making provision for backfilling the second triage nurse position when a nurse takes a meal break" | allocating a backfill position | MECH-FUND |
| "The North Metropolitan Health Service should consider engaging the services of sufficient numbers of Aboriginal Liaison Officers to service the Frankland Centre" | allocating ALO staff positions | MECH-FUND |
| "Allocate two additional psychiatric registrar positions" | direct allocation | MECH-FUND |
| "Increase funding for community mental health services so that a 24-hour crisis response is available" | the 24-hour crisis response (broader service redesign) | MECH-PROC |
| "Fund a training programme on family violence response for GPs" | the training programme | MECH-PROC |
| "Recruit and train additional ICU nursing staff at Westmead, and develop a backfill protocol for unplanned absences" | the protocol (multi-component but procedural endpoint) | MECH-PROC |

The "consider"/"give consideration to" / "review the need for" wrapper verbs **do not** push allocation recs out of FUND when allocation is the endpoint. This parallels the v2.1 ruling that "consider [regulatory action]" → code by contemplated mechanism if it's the endpoint, and the v2.1 INV ↔ PROC rule that endpoint matters, not the lead verb.

### Other mechanism rules carried forward from v2.2 unchanged

- **LEG ↔ PROC boundary by statutory status**, not document title (Mobile Crane Code of Practice → LEG; Industry Standard / Guideline → PROC).
- **"Consider [regulatory action]"** → code by the contemplated mechanism if it is the operational endpoint.
- **Multi-rec sets** → code by first-stated recommendation, with `ambiguous_mechanism=TRUE` if subsequent recs differ.
- **MECH-INV ↔ MECH-PROC operational-endpoint rule** — follow the verb chain to the last operational verb.

## Axis 3 — Addressee

*Unchanged from v2.2.* Nine mutually-exclusive: DEPT-NAMED, DEPT-GENERIC, HEALTH, REG, PROF, POLICE, COURT, PRIVATE, UNSPEC. See v2.2 for full content (HEALTH vs DEPT-NAMED, REG vs DEPT-NAMED, POLICE vs DEPT-NAMED rules; first-stated rule for multi-addressee blocks).

**Important framing change in v2.3:** the addressee axis carries the "who" question. The scope axis (re-framed below) carries the "what kind of change" question. Previously these were partially conflated in scope, which is what drove the α = -0.162 result on v2.2.

## Axis 4 — Specificity

*Categories unchanged from v2.2.* Binary: SPEC-2 (Specific), SPEC-1 (Aspirational). The `has_deadline_or_metric` boolean flag carries the v1.x SPEC-3 signal.

### Three clarifications in v2.3

**(a) Sharpen the "consider [verb chain]" exception.**

v2.2 ruled: "consider working with [named body] to develop [deliverable]" → SPEC-2 (the deliverable carries the specificity). v2.3 sharpens this:

- **The exception fires when:** "consider" is paired with a *specifiable downstream deliverable* — a form, protocol, training programme, register, equipment item, or other concrete artefact whose contents are themselves described. The named actor + specifiable deliverable carries the rec out of "mere consideration".
- **The exception does NOT fire when:** "consider" is the only operational verb without a downstream concrete deliverable; or the deliverable is itself another aspirational verb ("consider considering whether to...", "consider the need for further review").

**Worked example (Row 25, v2.2 pilot):** "I recommend to the Minister for Health that the department of cardiology at Westmead Hospital ... consider introducing a specific form of written consent for lead extraction procedures which include the following: [6 detailed items]" → **SPEC-2** (the exception fires — named actor + a consent form whose contents are listed in detail).

**Worked counter-example:** "I recommend that the Department consider the need for further review of training arrangements" → **SPEC-1** (no concrete deliverable; "review of training arrangements" is another aspirational verb chain).

**(b) Sharpen the named-actor test.**

A "named actor" is a specific entity that can be cited and held accountable. Generic role labels are NOT named actors, even when their function is clear from context.

- **Named actors:** "the Department of Health and Aged Care", "Royal Darwin Hospital", "the Commissioner of NSW Police Force", "AHPRA", "Western Sydney Local Health District", "the Minister for Police", "VicRoads", "WorkSafe Victoria", "the City of Palmerston Council".
- **NOT named actors:** "the relevant department", "the appropriate authorities", "those responsible", "those in the [industry]", "the relevant regulatory agencies", "stakeholders", "the medical profession", "policy makers", "key stakeholder organisations".

**Worked example (Row 37, v2.2 pilot):** "The relevant government department responsible for making recommendations to the Minister prior to the granting of the legal instrument ... ensure that adequate spectator safety measures have been implemented" → **SPEC-1** ("the relevant government department" is a role label, not a named actor — fails the named-actor test, regardless of the operational verb "ensure").

**(c) First-stated rule extended to specificity.**

v2.2 applied the multi-rec first-stated rule to mechanism, addressee, and scope. v2.3 extends it to specificity. When a rec block contains a vague first rec and specific subsequent recs, code by the first.

**Worked example (Row 13, v2.2 pilot):** "I recommend government and key stakeholder organisations give consideration to the issues and comments in this finding and give consideration to the development and implementation of strategies for the prevention of sudden infant deaths. **Specifically, I recommend that the Department of Health & Human Services adopt a lead role in: a. developing a single set of consistent guidelines** ..." → **SPEC-1** (first-stated: "government and key stakeholder organisations give consideration" — vague class + consider verb). Set `ambiguous_specificity=TRUE` because the second-stated rec is unambiguously SPEC-2.

### Tie-break rules (carried forward from v2.2)

- "Should consider" / "is encouraged to" → SPEC-1, unless the v2.3-sharpened exception fires (named actor + specifiable downstream deliverable).
- A recommendation that names only the action without a named actor is SPEC-1.

### The `has_deadline_or_metric` boolean flag

*Unchanged from v2.2.* Set on SPEC-2 rows.

## Axis 5 — Scope (re-framed as intervention-type in v2.3)

*This is the major v2.3 change.* The categories stay nominally the same (SCOPE-IND, SCOPE-SYS, SCOPE-MIX) but the definitions are re-framed to remove the addressee-anchoring that conflicted with the addressee axis.

**Why the re-framing was needed:** v2.2 said "names a single hospital → IND" AND "directed at a class → SYS", but had no rule for the dominant corpus case (single hospital + procedural change). On the v2.2 pilot, two coders applied two coherent but different readings: one took "single named entity → IND" literally; the other took "creates an ongoing policy → SYS regardless of addressee". α went negative (-0.162) because 12 of 40 clean rows split same-direction (all P1=IND/P2=SYS). The disagreement was not noise; it was the codebook conflating two axes.

**The fix:** strip the addressee-anchoring from scope. Addressee already carries the "who" question reliably (α 0.846). Scope carries the "what kind of change" question alone.

### Definitions (v2.3)

| Code | Label | Definition |
|---|---|---|
| SCOPE-IND | Individual / one-off | A discrete remedial action bounded to a single event, place, or person, that does **not** create or modify an ongoing system. |
| SCOPE-SYS | Systemic / ongoing | Creates or modifies an **ongoing** system: policy, protocol, guideline, register, training programme, audit framework, equipment standard, procedure, service redesign. Addressee type is irrelevant. |
| SCOPE-MIX | Mixed | Genuine span of both — retained for inter-rater work, but should be rare under v2.3. |

### The intervention-type test

For each recommendation, ask: **after this recommendation is implemented, will there be an ongoing system (policy / protocol / training / register / programme) that did not exist before, or did exist but has been modified?**

- **Yes** → **SCOPE-SYS**, regardless of whether the addressee is a single hospital, a state department, or a class of entities. The ongoing system can be bounded to one hospital and still be SCOPE-SYS — what matters is that something *ongoing* is created or modified, not the geographic / institutional scope of the change.
- **No** → **SCOPE-IND**. The action is a discrete one-off: a physical fix to a specific item, a single training event for a specific person, a written warning to a specific individual, compensation to a specific family, a one-off audit of a specific event.

### Worked examples (drawn from v2.2 pilot disagreement set)

| Text | Ongoing system created/modified? | Code |
|---|---|---|
| "City of Palmerston Council compile and maintain a register of all secured drains; inspect them three times per wet season" | Yes — ongoing register + inspection programme | SCOPE-SYS |
| "Royal Darwin Hospital should give consideration to making provision for backfilling the second triage nurse position" | Yes — ongoing staffing policy | SCOPE-SYS |
| "Arcare should review the Verification of Death Assessment form to include a tick-box on coronial reportability; undertake regular audits ≥6-monthly" | Yes — form revision + ongoing audit programme | SCOPE-SYS |
| "WA Seafood Exporters develop an awareness and training video" | Yes — ongoing training resource | SCOPE-SYS |
| "MNHHS undertake a review of liver biopsy risks with a view to establishing clear protocols and guidelines" | Yes — protocols and guidelines (endpoint) | SCOPE-SYS |
| "The Kalgoorlie Health Campus boundary fence should be raised urgently" | No — one-off physical fix to a specific fence | SCOPE-IND |
| "Refer the matter to AHPRA for consideration of disciplinary action against Dr X" | No — one-off referral about one named person | SCOPE-IND |
| "Provide a written apology and compensation to the family of the deceased" | No — one-off action affecting one named family | SCOPE-IND |
| "Reduce the speed limit on Tiger Brennan Drive between Berrimah Road and X from 100 to 80 km/h" | Yes — ongoing regulatory change at a specific road segment (the speed limit persists) | SCOPE-SYS |
| "Remove the specific ligature point in cell 5 at [Facility] identified during the inquest" | No — one-off physical fix to a specific cell | SCOPE-IND |

### Corpus distribution expectation

Under the v2.3 intervention-type rule, **SCOPE-SYS will dominate the Australian coronial corpus at ~90% modal share** (most coronial recommendations create or modify ongoing systems — protocols, training, policies, registers). SCOPE-IND will be rare (~5-10%, typically physical fixes, individual referrals, one-off remediations).

This is structurally skewed. The α metric will be punitive: on a binary axis at 90/10 modal split, expected-agreement-by-chance is 82%, so observed agreement needs to exceed ~96% for α ≥ 0.80. **Read scope by the skew-adjusted rule: % agreement ≥ 90% AND modal share ≥ 90% → Reliable.** The headline α number will be unstable and should be interpreted in the context of the modal distribution.

**Methodological note for the eventual manuscript:** the scope axis under v2.3 has near-degenerate analytical value for compliance prediction if 90%+ of recommendations fall in the same category. This is honest reporting of the corpus property, not a codebook flaw. The Phase 4 analysis ("does scope predict compliance?") may need to use scope as a binary indicator with explicit acknowledgement of the marginal-class imbalance.

### Multi-rec sets and the first-stated rule (carried forward from v2.2)

For rec blocks with mixed one-off + ongoing recs, code by the first-stated, with `ambiguous_scope=TRUE` if subsequent recs differ in intervention-type.

## Reading the IRR output

*Decision criterion updated for v2.3 scope.* Other axes unchanged.

`make irr` produces raw + clean α (clean filter fires when at least one rater used the catch-all stack).

**Reading rules:**
- **Theme, mechanism, addressee, specificity:** clean α ≥ 0.80 → Reliable.
- **Scope (skew-adjusted only):** the corpus distribution makes α structurally unstable. Read by % agreement ≥ 90% AND modal share ≥ 90% → Reliable. The α number is reported for transparency but is not the decision-criterion metric for this axis on this corpus.

## Pass 2 independence (carried forward from v2.2-retraction)

The two-LLM intra-rater protocol fails when both passes use the same model + same prompt + low temperature: identical inputs → identical outputs, α = 1.000 by construction. **Pass 2 must use either (a) a different model family from Pass 1 (e.g., Sonnet vs Opus), OR (b) verifiably-different prompt scaffolding sufficient to produce genuine independent judgement.** Diagnostic check after Pass 2: free-text `coder_notes` must differ from Pass 1's on a substantial proportion of non-empty rows; byte-identical notes = invalid pass.

**Success criterion for v2.3 pilot:** four axes (theme, mechanism, addressee, specificity) clean α ≥ 0.80; scope ≥ 90% raw agreement at ≥ 90% modal share (skew-adjusted Reliable). If achieved → freeze v2.3 as the pilot-proven codebook and proceed to second-human-rater recruitment.

If specificity stays Tentative (0.67-0.79), inspect specific disagreement-pair patterns rather than collapsing the binary further — SPEC-1 / SPEC-2 boundary requires interpretive judgement that may be near its alpha ceiling for LLM coders. If scope's raw agreement is below 90%, the intervention-type rule needs further worked-example calibration but the conceptual framing is sound.

**Failure modes to watch:**
- If mechanism α drops despite the Q3 fix → check whether the FUND ↔ PROC reframing pushed some staffing-related recs into the wrong tier; the codebook may need to add explicit worked examples for "fund + train" mixed recs.
- If theme or addressee α drops → almost certainly sample-drift, not codebook drift. Inspect rows.
- If scope α stays catastrophic → the intervention-type rule may itself have an ambiguous boundary (most likely: "ongoing register / log / audit framework" vs "one-off audit of a specific event"). Worked examples 10 and 5 in the table above target this directly; if they're not enough, add more.
